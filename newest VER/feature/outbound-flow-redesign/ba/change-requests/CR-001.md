# CR-001: Outbound Flow Redesign — Weigh-First + Cascading WEIGH-OUT

> **Date**: 2026-03-17
> **Requester**: Product Owner
> **Priority**: High
> **Complexity**: Complex
> **Status**: Approved (2026-03-17)

---

## 1. Change Summary

Redesign the outbound fulfillment flow from **Allocate-first** to **Weigh-first** model. The new sequence reflects the physical reality of bulk cargo operations where the empty truck is weighed before loading.

### Current Flow (AS-IS)
```
CREATE ORDER → ALLOCATE → PICK → LOAD → WEIGH-IN → WEIGH-OUT → SHIP
```

### Proposed Flow (TO-BE)
```
CREATE ORDER → WEIGH-IN → [per SKU: ALLOCATE+PICK → LOAD → WEIGH-OUT] → SHIP
```

> **Decision #1**: Interleaved per-SKU — Operator LOAD từng SKU rồi WEIGH-OUT ngay:
> `ALLOCATE+PICK SKU-1 → LOAD SKU-1 → WEIGH-OUT SKU-1 → ALLOCATE+PICK SKU-2 → LOAD SKU-2 → WEIGH-OUT SKU-2 → ... → SHIP`
>
> **Decision #2**: Giữ lại old endpoints `/allocate`, `/pick`, `/load` (deprecated but functional)
>
> **Decision #3**: Ship yêu cầu ALL lines phải WEIGH-OUT trước

## 2. Detailed Change Description

### 2.1 Step 4 — WEIGH-IN (trước Allocate)

**Current**: WEIGH-IN requires Order status = `Loaded | PartialLoaded`
**Proposed**: WEIGH-IN requires Order status = `Draft | Confirmed`

**Logic**: Xe rỗng vào cổng → lên cân → ghi GrossWeight (trọng lượng xe rỗng). Đây chính là Tare Weight về mặt vật lý, nhưng hệ thống ghi nhận là GrossWeight của lần cân đầu tiên (WEIGH-IN).

**Status transition**: `Draft/Confirmed → Weighing`

### 2.2 Step 5 — ALLOCATE + PICK by Line (SKU)

**Current**: 2 bước riêng biệt, xử lý toàn bộ Order cùng lúc
- `POST /orders/{id}/allocate` → allocate tất cả lines
- `POST /orders/{id}/pick` → pick tất cả lines

**Proposed**: 1 bước kết hợp, xử lý **từng Order Line (SKU)** riêng biệt
- `POST /order-details/{id}/allocate-and-pick` → allocate FIFO + pick cho 1 line cụ thể

**Logic**:
1. Operator chọn Order Line (SKU) cần xuất
2. Hệ thống FIFO allocate cho line đó
3. Ngay lập tức tạo WorkHeader (Pick) + post InventTrans STORAGE → STAGING
4. AllocationRecord.Status = Completed
5. Update OrderDetail: AllocatedQtyKg, PickedQtyKg, LineStatus = Picked
6. Header status = PartialPicked (nếu còn lines chưa pick) hoặc Picked (nếu tất cả done)

**Precondition**: Order status = `Weighing` (đã qua WEIGH-IN)

### 2.3 Step 6 — LOAD per Line (SKU)

**Current**: LOAD toàn bộ Order — `POST /orders/{id}/load` loads tất cả Picked lines
**Proposed**: LOAD **từng Order Line (SKU)** riêng biệt — interleaved với WEIGH-OUT

- `POST /order-details/{id}/load` → load cho 1 line cụ thể (Picked → Loaded)
- `POST /orders/{id}/load` → **DEPRECATED** — giữ lại, internally calls per-line cho tất cả Picked lines

**Logic**:
1. Operator chọn Order Line (SKU) đã Picked → LOAD lên xe
2. InventTrans pair: STAGING → SHIPPING cho line đó
3. Update OrderDetail: LoadedQtyKg = PickedQtyKg, LineStatus = Loaded
4. Header status cập nhật theo aggregation (PartialLoaded nếu còn lines chưa load)
5. **Ngay sau đó** → WEIGH-OUT cho SKU vừa LOAD (interleaved flow)

**Precondition**: OrderDetail.LineStatus = `Picked`

### 2.4 Step 7 — WEIGH-OUT (Cascading per SKU)

Đây là thay đổi lớn nhất. WEIGH-OUT xử lý theo 2 scenario:

#### Scenario A: Order có 1 SKU (1 Order Line)
1. Xe đầy lên cân → ghi TareWeight (= trọng lượng xe đầy)
2. Tạo 1 WeighbridgeLog:
   - `GrossWeightKg` = WEIGH-IN's GrossWeight (xe rỗng)
   - `TareWeightKg` = giá trị mới đo (xe đầy)
   - `NetWeightKg` = |Tare - Gross| (= trọng lượng hàng)
   - `resolved_item_id` = ItemId của SKU
   - `resolved_order_detail_id` = OrderDetail.Id
3. Cập nhật OrderDetail.WeighedQtyKg = NetWeightKg
4. Cập nhật OrderDetail.NetWeightKg = NetWeightKg
5. Status: OrderDetail → `Weighed`, OrderHeader giữ `Loaded` hoặc → custom state

#### Scenario B: Order có nhiều SKU (N Order Lines) — Cascading
Mỗi SKU được cân riêng. Quy trình lặp lại N lần:

**Lần cân thứ 1 (SKU-1):**
1. Sau khi LOAD SKU-1 lên xe
2. Xe lên cân → ghi weight = W1
3. Tạo WeighbridgeLog #1:
   - `GrossWeightKg` = W0 (= WEIGH-IN's GrossWeight, xe rỗng)
   - `TareWeightKg` = W1 (xe + SKU-1)
   - `NetWeightKg` = |W1 - W0| (= trọng lượng SKU-1)
   - `PreviousLogId` = WEIGH-IN log Id
   - `SequenceNo` = 1
   - `resolved_item_id` = SKU-1's ItemId
   - `resolved_order_detail_id` = OrderDetail of SKU-1
4. Cập nhật OrderDetail(SKU-1).WeighedQtyKg = NetWeightKg

**Lần cân thứ 2 (SKU-2):**
1. Sau khi LOAD thêm SKU-2 lên xe
2. Xe lên cân → ghi weight = W2
3. Tạo WeighbridgeLog #2:
   - `GrossWeightKg` = W1 (= **TareWeight của lần trước**)
   - `TareWeightKg` = W2 (xe + SKU-1 + SKU-2)
   - `NetWeightKg` = |W2 - W1| (= trọng lượng SKU-2)
   - `PreviousLogId` = WeighbridgeLog #1's Id
   - `SequenceNo` = 2
   - `resolved_item_id` = SKU-2's ItemId
   - `resolved_order_detail_id` = OrderDetail of SKU-2
4. Cập nhật OrderDetail(SKU-2).WeighedQtyKg = NetWeightKg

**Lần cân thứ N (SKU-N):** Tương tự, chain tiếp...

### 2.5 Step 9 — SHIP

**Current**: Requires `Loaded | Weighing`
**Proposed**: Requires **ALL OrderDetails** có LineStatus = `Weighed`

**Logic** (Decision #3 confirmed):
1. Validate: tất cả Order Lines phải có LineStatus = `Weighed`
2. Post InventTrans DEDUCTED cho từng line
3. Reverse EXPECTED từ SO
4. Update SO.ShippedQty, SO.Status
5. **Business Rule**: Nếu có line chưa Weighed → throw error, không cho Ship

## 3. Impact Analysis

### 3.1 Status Machine Changes

#### OrderStatus (Header) — Proposed
```
Draft → Confirmed → Weighing → Processing → Shipped
  (Cancelled ← any state)
```

- `Draft` → Create Order
- `Confirmed` → SO is approved, order ready
- `Weighing` → WEIGH-IN done (xe rỗng đã cân)
- `Processing` → Interleaved per-SKU operations in progress (allocate+pick+load+weigh-out per line)
- `Shipped` → All lines shipped

**Header status logic**:
- After WEIGH-IN → `Weighing`
- After first line ALLOCATE+PICK → `Processing` (stays Processing through all per-line ops)
- After SHIP → `Shipped`

**Changes**:
- Removed: `Allocated`, `PartialAllocated`, `Picking`, `PartialPicked`, `Picked`, `Loading`, `PartialLoaded`, `Loaded`
- Added: `Processing` (covers entire per-line interleaved phase)
- Rationale: Header no longer tracks granular line states; each line tracks its own status independently

#### OrderDetailStatus (Line) — Proposed
```
Pending → Picked → Loaded → Weighed → Shipped
  (Cancelled ← any state)
```

**Per-line status transitions**:
- `Pending` → chưa xử lý
- `Picked` → ALLOCATE+PICK done (FIFO allocated + picked from STORAGE → STAGING)
- `Loaded` → LOAD done (STAGING → SHIPPING, hàng đã lên xe)
- `Weighed` → WEIGH-OUT done (net weight calculated, WBLog created)
- `Shipped` → SHIP confirmed (InventTrans DEDUCTED)

**Changes**:
- Removed: `Allocated`, `PartialAllocated`, `PartialPicked`, `Loading`, `PartialLoaded` (per-line = no partial states needed)
- Clean linear flow per line: mỗi line hoặc chưa xử lý hoặc đã xong step đó

### Implications of Decision #1 (Interleaved)

Decision #1 introduces a significant design change: **LOAD must also be per-line** (not just Allocate+Pick). The interleaved cycle per SKU is:

```
Per SKU in Order:
  ALLOCATE+PICK (line) → LOAD (line) → WEIGH-OUT (line)
```

This means:
- **New endpoint needed**: `POST /order-details/{id}/load` (load single line)
- **Header status simplified**: `Processing` covers the entire interleaved phase
- **Each line tracks its own lifecycle independently**: Pending → Picked → Loaded → Weighed
- **UI needs per-line action buttons** in the Order Detail view
